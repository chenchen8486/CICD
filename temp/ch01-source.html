CI/CD 实用入门　/　第 1 章

第 1 章　先建立整体认识：CI/CD 能帮你做什么

面向算法与软件开发者　·　预计阅读 12 分钟　·　本章只需理解，不要求独立配置

　　你修改了一个数据处理函数，把代码推送到团队仓库。几分钟后，合并请求页面显示：格式检查通过，12 个单元测试通过，软件包构建成功。CI/CD 就在这段等待时间里完成了自动验证。

　　本章先回答三个问题：代码提交后发生了什么，Git 与 CI/CD 各自负责什么，以及为什么团队要把这些检查交给机器。读完后，看到团队仓库里的流水线状态，就能理解它与自己的代码改动有什么关系。

  1. 1.1 从一次代码提交说起：认识提交、检查、反馈和修复的闭环。
  2. 1.2 Git、CI 平台与 Runner 的分工：弄清每个角色负责什么。
  3. 1.3 团队通常自动检查什么：了解格式检查、测试、构建与结果归档。
  4. 1.4 CI、持续交付与持续部署：区分自动验证和两种发布方式。
  5. 1.5 看一条最小流水线：把概念对应到实际配置。

1.1 从一次代码提交说起

　　假设你正在维护一个 Python 算法项目。你创建了自己的分支，修改数据清洗逻辑，补充了一个测试，然后执行 git push。push 会把本地提交上传到远程仓库，但它本身不会运行测试。仓库托管平台发现新提交后，根据项目里的 CI 配置创建一条流水线，再由 Runner 执行具体命令。

　　运行结果会回到分支或合并请求页面。检查失败时，你修改代码并再次推送，新提交会触发新一轮验证。这样就形成了“提交、自动检查、反馈、修复”的闭环。

　　这条链路里最容易混淆的是触发与执行。CI 平台负责接收事件、展示状态、调度任务，Runner 负责运行安装依赖、执行测试等命令。你可以把 CI 平台看作任务看板，把 Runner 看作真正干活的电脑。

1.2 Git、CI 平台与 Runner 的分工

　　Git 是版本管理工具，记录谁在什么时候改了什么。GitLab 提供远程仓库、合并请求和 CI/CD 页面。Runner 是独立于网页界面的执行程序，负责运行配置中的命令。本书后续统一以 GitLab 为例，不再在不同平台之间切换。

角色主要负责你需要关注
Git记录提交、分支和版本历史改动是否提交，分支是否正确
远程仓库保存团队代码，承载分支与合并请求代码是否推送成功
CI 平台接收事件，创建流水线，展示结果哪条流水线正在运行
Runner在机器或容器中执行检查命令哪个任务失败，日志里有什么错误
你与同事修复问题，评审代码，决定是否合并结果是否可信，改动是否合理

　　因此，“Git 会 CI/CD”这个说法不够准确。Git 提供版本和事件来源，GitLab 读取仓库中的配置并组织自动化。进入项目后，左侧“代码”区域用于文件、分支和 MR，“构建”区域用于流水线、Job 和产物。若只看见一排图标，先点击页面左上角菜单按钮展开侧栏。不同 GitLab 版本可能合并或调整菜单，但功能归属不变。

1.3 团队通常自动检查什么

　　CI 的价值在于把重复检查放到每次改动之后。以前可能由某个人合并前手动运行，现在每次推送都能执行同样的命令，团队更容易及时发现是哪次提交引入了问题。

  • 格式与静态检查：检查代码风格、未使用变量、明显类型错误等问题。
  • 单元测试：验证函数或模块在已知输入下是否得到预期结果。
  • 集成测试：验证多个模块、服务或数据流程能否一起工作。
  • 构建与打包：确认项目能生成可安装、可分发的软件包。
  • 保存结果：归档测试报告、覆盖率报告和构建产物，方便团队查看。

　　算法项目还可以用小数据集做快速冒烟验证。例如，检查预处理流程能否跑完、模型输出形状是否正确、结果中是否出现 NaN。这里的重点是“用较小成本发现明显错误”，不代表每次提交都要完整训练模型。耗时较长的训练与完整评估通常需要单独安排。

　　流水线通过只表示已配置的检查通过。测试没有覆盖的逻辑仍可能有错，算法指标是否符合业务要求也需要合适的评估数据。CI 让验证稳定地发生，验证是否充分仍由团队负责。

1.4 CI、持续交付与持续部署

　　CI 是 Continuous Integration，中文叫持续集成。开发人员频繁把改动集成到团队代码中，并通过自动构建和测试尽早发现问题。对多数初学者来说，日常接触最多的就是这一部分。

　　CD 可能指 Continuous Delivery，也可能指 Continuous Deployment。前者叫持续交付，代码经过验证后保持可发布状态，正式发布由人确认。后者叫持续部署，通过验证的改动会自动发布到目标环境。两者都要求前面的验证可靠，区别在最后的发布动作是否自动执行。

　　学习算法或业务代码开发时，不需要一上来就配置自动部署。先让每次提交都完成可靠的检查与测试，再谈发布。很多内部算法项目只需要 CI 和构建产物，根本没有持续部署环节，这也是正常选择。

1.5 看一条最小流水线

　　下面是一份 GitLab CI 的简化示例。文件名为 .gitlab-ci.yml，放在仓库根目录。它使用 Python 3.12 环境，安装项目依赖和 pytest，然后运行测试。这里先观察结构，第 5 章会逐行讲解更完整的配置。

image: python:3.12

test:
  script:
    - python -m pip install -r requirements.txt pytest
    - python -m pytest

　　image 指定任务使用的容器镜像，test 是任务名称，script 下面是 Runner 要执行的命令。仓库中存在有效配置、满足触发条件并且有可用 Runner 时，GitLab 就能创建并运行相应流水线。

　　如果第二行测试命令返回失败状态，这个任务通常会显示失败，流水线也会把结果反馈给你。点击失败任务可以看到日志。你后续要做的大量工作，就是阅读这些结果并修复对应问题。

本章小结

　　现在可以把 CI/CD 看成团队仓库旁的一套自动检查机制。你负责提交清晰的小改动，Git 保存版本，CI 平台组织流程，Runner 执行命令，团队根据结果决定修复、评审或合并。

  • push 上传提交，CI 配置决定后续自动执行什么。
  • CI 的重点是频繁集成与自动验证，不等于自动发布。
  • 持续交付保留人工发布确认，持续部署会自动发布。
  • 流水线通过代表已配置检查通过，代码评审和测试设计仍然重要。

第 2 章　日常协作流程：从写代码到合并

面向算法与软件开发者　·　预计阅读 15 分钟　·　本章需要理解并照着操作

　　团队协作的重点不只是把代码推上去，还要让每次改动有清晰边界、有可验证结果，并且能被同事理解和复查。功能分支、合并请求与 CI 共同支撑这个过程。

　　本章以一个 Python 算法项目为例，走完从同步主分支到合并代码的完整流程。文中的 main 代表团队默认主分支，如果项目使用 master 或其他名称，替换为实际名称即可。

  1. 2.1 一套完整的日常协作流程：先看懂各环节怎样衔接。
  2. 2.2 从最新主分支创建功能分支：给本次改动一个独立边界。
  3. 2.3 本地检查、提交与推送：形成可追溯的版本。
  4. 2.4 发起一个清楚的合并请求：让机器和同事都能验证改动。
  5. 2.5 处理 CI 与评审意见：用新提交完成修复。
  6. 2.6 合并之后做什么：同步主分支并整理本地环境。
  7. 2.7 一次完整协作：谁负责什么：用角色时序图串起提交、检查、修复与合并。

2.1 一套完整的日常协作流程

　　一次规范的改动通常从最新主分支开始。开发工作在功能分支上完成，本地检查通过后提交并推送，再通过合并请求说明改动。CI 负责重复执行自动检查，评审人员负责判断设计、可读性和潜在风险。两类检查都满足团队要求后，代码才进入主分支。

　　这条流程不需要每个项目都完全相同。有的团队要求先创建合并请求再运行 CI，有的团队在每次推送时就运行 CI。操作顺序可以调整，核心原则保持一致：改动有边界，结果可验证，合并且有依据。

2.2 从最新主分支创建功能分支

　　开始新任务前，先检查工作区是否还有未提交改动，再同步主分支。直接在有未提交改动的工作区切换分支，可能把旧任务带到新任务中，也可能因文件冲突而无法切换。

git status
git switch main
git pull origin main
git switch -c feature/normalize-input

　　下面四行命令按顺序执行，每行对应一个步骤：

  1. git status：查看当前分支和未提交改动。先确认工作区状态，再决定是否切换分支。
  2. git switch main：切换到本地主分支，让后续操作从主分支开始。
  3. git pull origin main：从远程仓库获取主分支的最新改动，并更新本地主分支。origin 是远程仓库的常用名称。
  4. git switch -c feature/normalize-input：创建并立即切换到功能分支，接下来的修改会留在这个分支上。

　　分支名应能说明任务，例如 feature/normalize-input 表示输入归一化功能。团队已有命名规范时，优先遵循团队规范。

　　功能分支用于隔离本次工作。主分支上的其他改动不会自动进入该分支，因此任务周期较长时，需要按团队习惯定期同步主分支，减少最后合并时的冲突。

2.3 本地检查、提交与推送

　　修改代码后，先在本地运行能够覆盖本次改动的检查。算法项目至少要确认相关函数测试通过，涉及数据处理时还应检查空输入、异常值和输出形状。CI 会再次执行团队配置的检查，本地验证可以提前减少无效往返。

　　提交前查看变更，确认没有误加临时文件、数据集、模型权重或密钥。一个提交尽量围绕一个明确目的，提交说明直接写出做了什么，例如“修复空输入导致的预处理异常”。

python -m pytest
git status
git diff
git add src/preprocess.py tests/test_preprocess.py
git commit -m "修复空输入导致的预处理异常"
git push -u origin feature/normalize-input
  1. python -m pytest：先运行项目测试，确认代码行为符合预期。测试失败时先修复，不要继续提交。
  2. git status：查看哪些文件被修改、哪些已暂存、哪些还未被 Git 管理，防止漏交或误交文件。
  3. git diff：查看尚未暂存的具体代码差异，逐处确认本次修改是否符合预期。
  4. git add src/preprocess.py tests/test_preprocess.py：只把这两个文件放入暂存区。暂存区保存准备纳入下一次提交的改动。
  5. git commit -m "修复空输入导致的预处理异常"：把暂存的改动记录为一个本地提交，-m 后面的文字是提交说明。
  6. git push -u origin feature/normalize-input：把本地功能分支推送到远程仓库。-u 会记录本地与远程分支的对应关系，后续通常只需执行 git push。

2.4 发起一个清楚的合并请求

　　推送后，在 GitLab 创建 Merge Request，在 GitHub 创建 Pull Request。它们都用于把源分支的改动合并到目标分支。源分支选择刚推送的功能分支，目标分支通常是主分支。

　　PR 是 Pull Request 的缩写，MR 是 Merge Request 的缩写。两种名称对应的协作动作基本一致：请求把源分支合并到目标分支，并在合并前完成 CI 检查和代码评审。本手册后续统一使用 GitLab 的 MR 叫法。

在 GitLab 页面中创建 MR

　　先登录公司 GitLab，进入团队项目。在左侧菜单选择“代码 > 合并请求”，英文界面是 Code > Merge requests。页面列出开放中、已合并和已关闭的 MR，点击标题可以进入详情。

  1. 在自己有权限的团队项目中，点击右上角“新建合并请求”或 New merge request。
  2. Source branch 选择 feature/normalize-input，Target branch 选择 main。这里决定代码从哪里来、要合并到哪里，不要选反。
  3. 点击 Compare branches and continue，填写标题和说明。标题直接写改动，例如“修复空输入导致的预处理异常”。
  4. 按团队要求选择评审人 Reviewer 和负责人 Assignee。评审人负责提出意见，负责人通常跟踪本次改动，具体分工以团队约定为准。
  5. 点击 Create merge request。进入详情页后查看流水线状态、代码差异和讨论，不需要另建一个 MR 来接收后续修复。

　　如果找不到创建按钮，先确认是否登录、是否进入了自己的项目而不是只读公开页面，再确认账号是否有项目权限。界面名称可能随 GitLab 版本略有变化，但入口都在项目的合并请求区域。

MR 说明写什么

　　一个便于评审的合并请求，应让同事不看代码也能知道改动的目的和验证情况。正文至少写清以下内容：

  • 改动内容：修改了哪些函数、配置或测试。
  • 改动原因：解决什么缺陷或满足什么需求。
  • 验证方式：运行了哪些测试，覆盖了哪些关键输入。
  • 注意事项：是否影响数据格式、接口、依赖或后续工作。

　　合并请求创建后，团队成员看到的就是同一份代码、同一条 CI 结果和同一组讨论记录。需要补充说明时，优先写在合并请求中，避免重要结论只留在私人聊天里。

2.5 处理 CI 与评审意见

　　CI 失败时，先打开失败任务，找到第一条有效错误，判断是代码问题、测试问题还是运行环境问题。能在本地复现时，先修复并重新运行相同检查。确认修复后，在正常功能分支上产生一个新提交并推送，流水线会基于最新提交重新验证。

python -m pytest
git add src/preprocess.py
git commit -m "补充空列表的分支处理"
git push
  1. python -m pytest：修复代码后重新运行测试，先在自己的电脑上确认原问题已经解决。
  2. git add src/preprocess.py：把这次修复的文件放入暂存区，准备形成新的提交。若还改了测试或其他文件，也要检查并添加对应文件。
  3. git commit -m "补充空列表的分支处理"：为这次修复创建本地提交。提交说明直接写出补充了什么处理。
  4. git push：把新提交推送到已有远程功能分支。推送后，团队可以在合并请求中查看修复和新一轮 CI 结果。

　　这四行构成“本地验证、选择改动、创建提交、推送复查”的修复流程。第一次提交后发现问题，不需要删除原合并请求，在同一功能分支追加提交即可。

　　评审意见需要逐条回应。接受意见就修改代码，存在不同判断就结合具体场景说明理由。修复后标记对应讨论已解决，便于评审人员确认。不要为了让历史看起来整洁而随意强推公共分支，需要改写已推送历史时，先确认团队规则。

　　CI 通过与评审通过解决的问题不同。CI 能证明配置的命令执行成功，评审人员还会检查测试是否有效、算法逻辑是否合理、改动是否影响其他模块。两者不能互相替代。

2.6 合并之后做什么

　　达到团队的合并条件后，再执行合并。合并方式可能包括普通合并、压缩合并或变基后合并，具体选择由团队仓库规则决定。不要在不了解团队历史规范时自行更改。

　　合并完成后，本地工作区仍停留在旧功能分支。切回主分支并拉取最新代码，确认刚才的改动已经进入主分支。已经不再需要的本地和远程功能分支，可以按团队习惯删除。

git switch main
git pull origin main
git branch -d feature/normalize-input
  1. git switch main：从已经完成工作的功能分支切回本地主分支。
  2. git pull origin main：获取远程主分支的最新状态，把刚合并的改动同步到本地。
  3. git branch -d feature/normalize-input：删除不再需要的本地功能分支。如果分支尚未合并，Git 通常会拒绝删除。这里不会删除远程分支，不要为了绕过保护而随意使用强制删除。

2.7 一次完整协作：谁负责什么

　　前面分别介绍了操作命令，本节把角色和动作串成一条完整链路。代码提交者负责发起改动并修复问题，CI 平台负责自动检查，评审人员负责判断设计与代码质量，有合并权限的人负责最终合并。

　　PR/MR 是团队共享的协作页面，不是单独发给某一位同事的消息。下图从上往下按时间阅读，数字表示一个典型的执行顺序。

　　以“修复空输入导致的预处理异常”为例。你在自己的功能分支提交代码，推送后创建 PR/MR，目标分支选择 main。到这里，你完成了改动的发起，后续不需要把代码单独发给同事手动测试。

　　PR/MR 创建或更新后，满足触发条件时，CI 平台创建流水线，Runner 自动执行格式检查和 pytest 等命令。评审人员不需要替你运行这些测试，你们查看的是同一份代码和同一组检查结果。

　　如果空输入测试失败，平台会在 PR/MR 中显示失败状态。你打开失败 Job 的日志，修改代码并推送新提交，原 PR/MR 会更新，CI 重新检查。这是图中第 3、4 步，可以重复多次。若原因是 Runner 故障或权限不足，再把失败任务链接和关键日志提供给负责流水线或环境维护的同事。

　　自动检查通过后，评审人员检查算法逻辑、接口影响和测试是否有效。如果有意见，对方在 PR/MR 中提出问题，你修改、回应并推送，再次接受检查和评审。对应图中的第 6、7 步，也可以重复。

　　当 CI 与评审都满足团队要求后，有权限的人执行合并。评审人员和合并负责人可能是同一位同事，也可能不同，取决于团队规则。合并后，你同步主分支，再开始下一项任务。

本章小结

　　日常协作可以固定为一条简单路径：同步主分支，创建功能分支，本地修改与检查，提交并推送，创建合并请求，处理 CI 和评审结果，最后合并并同步主分支。

  • 本地验证用于尽早发现问题，CI 用于在团队环境中重复验证。
  • 提交说明和合并请求说明都应让同事快速理解改动。
  • 修复 CI 或评审问题时，在正常功能分支上追加提交并推送。
  • 合并后同步主分支，再开始下一个任务。

第 3 章　必须掌握的 CI/CD 核心概念

面向算法与软件开发者　·　预计阅读 15 分钟　·　目标是看懂团队流水线

　　流水线页面上的 Pipeline、Job、Runner 等名词，描述的是同一件事的不同层级：为什么启动，任务怎样分组，命令在哪里运行，生成的文件如何保存。

　　本章把这些概念放进一个 Python 项目中解释。读完之后，看到一条流水线时，应能说出它由哪些任务组成、任务由谁执行，以及失败日志和生成文件分别在哪里。

  1. 3.1 Trigger：流水线为什么启动：认识推送、合并请求、手动和定时触发。
  2. 3.2 Pipeline、Stage、Job 与 Step：理解流程的层级关系。
  3. 3.3 Runner：任务在哪里执行：理解执行环境和任务隔离。
  4. 3.4 Artifact 与 Cache：区分结果保存与依赖缓存。
  5. 3.5 变量与运行环境：理解配置输入和环境边界。
  6. 3.6 把概念对应到一份配置：在 YAML 中找到本章概念。

3.1 Trigger：流水线为什么启动

　　Trigger 中文是触发条件，回答“发生什么事件时创建一条流水线”。常见来源包括推送分支、创建或更新合并请求、手动点击运行、定时计划以及创建版本标签。团队通过触发规则决定哪些事件需要自动检查。

　　版本标签的英文是 Tag。它是 Git 给某个提交添加的固定标记，例如 v1.2.0，常用于标识准备发布的版本。分支会随着新提交向前移动，标签通常固定指向一个提交。

  • 推送触发：功能分支每次推送后运行快速检查和单元测试。
  • 合并请求触发：重点验证准备进入主分支的改动。
  • 手动触发：执行耗时评估、构建候选版本等需要人工决定何时启动的任务。
  • 定时触发：每天运行完整测试或耗时较长的算法回归评估。

　　算法回归评估是用固定数据和评价指标检查新旧版本，确认改动没有让已有效果变差。用作比较基准的旧结果叫基线，例如准确率、召回率或耗时。回归评估关注“改动前后有没有退化”，不等同于重新训练模型。

　　触发只决定何时创建流程，不决定流程里具体执行什么。具体任务由仓库中的 CI 配置定义，部分任务还可能附带额外条件，因此流水线启动不代表所有 Job 都会运行。

3.2 Pipeline、Stage、Job 与 Step

　　Pipeline 是流水线，表示一次完整的自动化运行。满足触发条件时，一次推送可以产生一条新的流水线，里面可以有多个任务。Stage 是阶段，用于安排任务顺序，例如先检查、再测试、最后构建。

　　Job 是一项独立任务，例如单元测试。Step 是 Job 内按顺序执行的一步，在 GitLab 中通常体现为 script 列表的一项，在 GitHub Actions 中对应 steps 中的一项。Job 有独立的状态和日志，Step 是组成 Job 的具体动作。

　　并行表示多个 Job 同时运行，不必依次排队。例如单元测试和集成测试互不依赖，就可以并行缩短等待时间，前提是 Runner 资源足够。GitLab 的常规阶段模式中，后续阶段默认等待前一阶段的 Job 完成。

　　needs 用来明确指定“当前 Job 依赖哪些前置 Job”，可以让有依赖关系的任务更精确地衔接，第 5 章再展开。

　　查看失败时，先定位 Pipeline，再定位失败 Job，最后阅读 Job 日志中的具体命令。这个顺序比从流水线首页猜测原因更有效。

3.3 Runner：任务在哪里执行

　　Runner 是安装在机器上、接收并执行 CI 任务的程序。CI 平台负责分配 Job，Runner 负责拉取代码、准备环境、执行命令并回传状态和日志。GitHub Actions 中也叫 Runner，Jenkins 中常见的对应概念是 Agent。

　　Runner 可以使用容器提供相对独立的运行环境。容器可以理解为隔离出来的一套运行空间，容器镜像则是创建这个空间的模板。镜像中预先装有操作系统组件和工具，但不等于你的完整项目环境。

　　image: python:3.12 表示使用带 Python 3.12 的镜像。项目依赖仍需按配置安装。不同 Job 可能由不同 Runner 或容器执行，因此不能默认前一个 Job 留在工作目录里的临时文件一定会出现在下一个 Job 中。

　　自托管 Runner 指团队自己准备和维护的执行机器，常用于访问内网数据或使用 GPU 等特定硬件。平台托管的 Runner 则由平台准备。Runner 是否在线、是否接受该项目任务、是否具备所需工具，会直接影响流水线能否启动。

3.4 Artifact 与 Cache：保存结果还是加速

　　Artifact 中文叫任务产物，指本次运行生成、需要保留的文件，例如测试报告和构建包。Cache 中文叫缓存，用于保存可重新获取的依赖文件，减少下一次安装的等待时间。缓存丢了通常可以重建，产物丢了则可能需要重新运行任务。

　　wheel 是 Python 的一种软件包格式，文件后缀为 .whl，可供其他人安装。pip 是 Python 常用的包安装工具，npm 常用于 JavaScript 项目的包管理。理解用途即可，本章不要求掌握这些工具的打包细节。

对比项ArtifactCache
主要目的保存本次运行的结果复用依赖，提升速度
常见内容测试报告、构建产物、日志pip、npm 等依赖缓存
是否属于交付结果是否
丢失后的影响无法下载或传递该结果重新下载依赖，通常仍可完成
能否当作可靠数据源可以按团队保存策略使用不可以，缓存不保证始终存在

　　不要从缓存目录读取构建结果或测试报告。缓存可能失效、被清除或由不同 Runner 分别保存。需要明确传递的结果应使用 Artifact 或团队规定的制品库。制品库是集中保存软件包等交付文件的服务，便于长期管理和复用。

3.5 变量与运行环境

　　CI 变量用于向任务传入配置，例如测试数据目录、报告文件名或运行模式。把变化的信息放进变量，可以避免为了换目录或模式而修改代码。GitLab 会预先生成一些变量，称为预定义变量，项目也可以定义自己的变量。

　　CI_COMMIT_SHA 表示本次提交的 SHA，也就是 Git 为提交生成的唯一标识字符串，界面常只显示前几位。CI_PIPELINE_ID 表示流水线编号，用于区分不同的运行记录。

　　运行环境指代码运行时依赖的机器、操作系统、软件版本、网络权限和配置。开发环境用于写代码，测试环境用于验证，生产环境则面向实际业务或用户。这些环境可以使用不同的地址和权限。

　　CI 的 Runner 环境与个人电脑可能不同。本地已经安装的包、存在的文件和设置的变量不会自动出现在 CI 中，这也是“本地通过、CI 失败”的常见原因。

　　密码、访问令牌和私钥都是敏感凭证，应放入平台提供的受保护变量或密钥管理功能，不写进仓库中的 YAML。受保护变量通常只对符合平台规则的分支或标签开放，具体范围由团队配置。任务能否访问内网数据，也取决于网络和权限设置。

3.6 把概念对应到一份配置

　　下面的 GitLab CI 示例把本章概念放在一起。YAML 是一种常用配置文本格式，通过缩进和“键: 值”表达结构。YAML 使用空格缩进，不用 Tab。同级配置要保持相同缩进。

　　示例包含检查、测试、构建三个阶段，使用 Python 3.12 镜像，缓存 pip 文件，保存测试报告和构建包。这里先理解各配置块的作用，第 5 章再逐项修改。

stages: [check, test, build]

default:
  image: python:3.12
  before_script:
    - python -m pip install -r requirements.txt ruff pytest build

variables:
  PIP_CACHE_DIR: "$CI_PROJECT_DIR/.cache/pip"

cache:
  key:
    files: [requirements.txt]
  paths: [.cache/pip]

lint:
  stage: check
  script:
    - python -m ruff check .

unit_test:
  stage: test
  script:
    - python -m pytest --junitxml=report.xml
  artifacts:
    when: always
    paths: [report.xml]
    reports:
      junit: report.xml

package:
  stage: build
  script:
    - python -m build
  artifacts:
    paths: [dist/]

　　stages 声明三个阶段的顺序。default 为 Job 提供共同默认值，before_script 中的命令会在每个 Job 的 script 之前执行，这里用于安装依赖和工具。

　　variables 定义所有 Job 可用的变量。PIP_CACHE_DIR 告诉 pip 把缓存写入哪个目录，CI_PROJECT_DIR 是 GitLab 提供的项目目录。这里让 pip 的实际缓存目录与下面声明的保存目录保持一致。

　　cache.paths 指定要缓存的目录。key.files 让缓存标识随 requirements.txt 的内容变化，依赖清单变化后可以使用新的缓存，避免一直复用旧内容。

　　lint、unit_test 和 package 都是自定义的 Job 名称。stage: check 等字段把 Job 放入前面声明的阶段。Ruff 是 Python 静态检查工具，可以发现未使用的导入等问题，命令末尾的点表示检查当前目录。

　　--junitxml=report.xml 让 pytest 额外生成 JUnit XML 报告。XML 是记录结构化数据的文本格式，JUnit XML 则约定怎样记录测试通过和失败的信息，便于 CI 平台展示。when: always 表示成功或失败都保存报告。

　　python -m build 调用 Python 的构建工具生成软件包，dist/ 是默认输出目录，artifacts.paths 指定把其中的文件保存为 Artifact。实际项目还需要相应的 Python 打包配置，第 9 章会结合完整项目说明。

　　这份示例没有显式编写触发规则，实际触发行为会受到平台默认规则、项目现有配置和分支条件影响。修改团队流水线前，先阅读已有配置，不要直接覆盖。

本章小结

　　Trigger 决定何时启动，Pipeline 组织本次流程，Stage 划分阶段，Job 执行具体任务，Runner 提供运行环境，Artifact 保存结果，Cache 加速依赖复用。变量与环境配置则为任务提供输入和边界。

  • 排查失败时，按 Pipeline、Job、具体命令逐层定位。
  • 不要假设不同 Job 一定共享同一台机器和临时目录。
  • 需要保存和传递的结果用 Artifact，依赖加速用 Cache。
  • 密钥不写入仓库，运行环境差异要在配置中明确处理。

第 4 章　团队项目在 CI 中检查什么

面向算法与软件开发者　·　预计阅读 16 分钟　·　目标是理解检查内容并会运行

　　CI 只会执行团队提前配置的检查。测试文件、检查规则和构建命令由团队准备，Runner 负责重复执行，不会自动理解算法是否正确。

　　本章介绍常见的检查类型，以及它们适合发现的问题。你不需要一次配齐所有检查，先理解项目已有的命令，再逐步补充有效验证。

  1. 4.1 从快速检查到完整评估：按成本和覆盖范围分层。
  2. 4.2 格式与静态检查：不运行完整业务也能发现基础问题。
  3. 4.3 单元测试与集成测试：分别验证局部和协作行为。
  4. 4.4 构建与打包：确认项目能形成交付物。
  5. 4.5 算法项目的专项检查：检查形状、数值与指标。
  6. 4.6 怎样安排检查时机：平衡反馈速度和运行成本。

4.1 从快速检查到完整评估

　　静态检查主要分析代码文本和结构，单元测试验证一个函数或模块，集成测试验证多个部分能否协作，构建检查项目能否打包。算法项目还可能用固定数据评估准确率、召回率或耗时。

　　这些检查不是互相替代的关系。格式正确不代表逻辑正确，单元测试通过也不代表完整数据流程一定正常。团队通常把便宜、快速的检查放在每次提交时，把耗时任务放到定时或手动流程。

4.2 格式与静态检查

　　格式检查关注缩进、空格和排版是否一致，静态检查还能发现未使用的导入、未定义名称等问题。Ruff 是 Python 常用的检查工具，下面的命令需要先安装 Ruff，CI 中也必须包含安装步骤。

python -m ruff check .
python -m ruff format --check .
  1. python -m ruff check .：检查当前目录的 Python 代码，发现规则命中的问题时返回失败状态。
  2. python -m ruff format --check .：只检查格式是否一致，不修改文件。加上 --check 后，它适合用于 CI 验证。

　　格式化与静态检查的目标不同。格式化统一代码外观，静态检查寻找潜在错误。团队选择哪些规则，应写在项目配置中，避免每个人本地使用不同标准。

4.3 单元测试与集成测试

　　单元测试用已知输入验证一个小单元的输出，例如归一化函数是否返回正确比例。集成测试把多个真实模块连起来，例如读取数据、预处理、推理和保存结果能否依次完成。

　　pytest 是测试运行工具，不是测试文件本身。开发人员把测试写在 test_*.py 等文件中，pytest 按发现规则收集并执行。下面的命令展示两种常见运行范围：

python -m pytest tests/test_preprocess.py
python -m pytest tests/ -k normalize
  1. python -m pytest tests/test_preprocess.py：只运行预处理测试文件，适合修改某个模块后快速验证。
  2. python -m pytest tests/ -k normalize：在测试目录中选择名称包含 normalize 的测试，-k 是 pytest 的名称筛选参数。

　　测试中的固定输入和预期结果叫测试夹具或测试样例，英文常写 fixture。fixture 也可以包括临时目录、模拟对象等准备工作。它的作用是让每次测试从可重复的条件开始。

4.4 构建与打包

　　构建把源代码和元数据转换成可安装、可分发的结果。Python 项目常生成 wheel 和 sdist。wheel 用于安装，sdist 是源代码发行包，通常以 .tar.gz 结尾。

python -m build

　　这行命令调用 Python 的 build 工具读取项目打包配置，默认把结果写入 dist/。只有命令成功还不够，团队还可以检查包内是否漏文件，并在干净环境中试安装。

　　构建产物通常保存为 Artifact，供后续任务或发布流程使用。构建配置、依赖清单和测试文件都应随代码一起评审，避免只修改功能而漏掉交付配置。

4.5 算法项目的专项检查

　　算法项目除了普通单元测试，还常用小数据集做冒烟测试。冒烟测试指用较小输入走通关键流程，尽早发现崩溃、接口不接或明显输出异常，不代表完整评估模型效果。

　　下面的测试检查归一化输出的长度、数值有效性和总和。它对应第 9 章的完整项目：

import math

from algorithm_demo.preprocess import normalize


def test_normalize_output():
    result = normalize([1.0, 3.0])
    assert len(result) == 2
    assert all(math.isfinite(value) for value in result)
    assert math.isclose(sum(result), 1.0)
  1. len(result) == 2：检查输出数量与两个输入对应，防止结果意外增多或丢失。
  2. math.isfinite(value)：检查数值是有限值，能发现 NaN 和正负无穷。NaN 表示无法定义或无法表示的数值结果。
  3. math.isclose(sum(result), 1.0)：检查总和接近 1。浮点计算存在微小误差，通常不直接用绝对相等判断。

　　指标门槛用于阻止效果退化，例如要求固定评估集上的准确率不低于 0.90。数据版本、指标定义和阈值都要明确，否则不同运行之间无法公平比较。门槛应根据项目基线制定，本书不替你设定统一数值。

4.6 怎样安排检查时机

　　流水线并非越长越好。每次提交都运行数小时任务，会降低反馈速度，也会占用 Runner。可以按下面的方式分层，具体时长以项目实测为准。

检查内容常见时机主要目的
格式、静态检查、快速单元测试功能分支推送、PR/MR 更新尽快发现基础问题
集成测试、小数据集冒烟PR/MR、合并到主分支验证关键链路
完整数据集评估、长时间训练定时或手动控制成本并观察整体效果
构建候选版本主分支、版本标签或手动形成可交付结果

　　覆盖率表示测试执行到了多少代码，常见指标是行覆盖率。覆盖率可以帮助发现完全没测试的区域，但高覆盖率不代表断言有效，也不代表算法指标达标。

本章小结

　　CI 中的每项检查都应有明确目的。静态检查看基础质量，单元测试看局部行为，集成测试看模块协作，构建看交付能力，算法专项检查看数值与指标。

  • 测试和规则由团队提前准备，CI 与 Runner 负责自动执行。
  • 冒烟测试用较小成本走通关键流程，不等于完整模型评估。
  • 输出形状、有限数值和指标门槛是算法项目的常见检查。
  • 快速检查频繁运行，耗时任务按成本定时或手动运行。

第 5 章　看懂并修改 GitLab CI 配置

面向算法与软件开发者　·　预计阅读 18 分钟　·　目标是能看懂并做小范围修改

　　GitLab CI 的配置文件通常是仓库根目录下的 .gitlab-ci.yml。它告诉平台何时创建任务、任务按什么顺序执行，以及保存哪些结果。

　　本章片段只展示相关字段，不一定是可直接运行的完整文件。第 9 章会把所有必要配置放进一个完整项目。

  1. 5.1 先分清配置的层次：全局默认值、任务和命令。
  2. 5.2 触发条件与 rules：控制流水线与任务是否出现。
  3. 5.3 stages 与 needs：安排阶段顺序和精确依赖。
  4. 5.4 artifacts 与 cache 配置：保存结果或加速安装。
  5. 5.5 手动任务：把高成本操作交给人工决定。
  6. 5.6 安全修改配置：小改动、先验证、再合并。
  7. 5.7 常见配置错误：从现象反查配置。

5.1 先分清配置的层次

　　stages、default、variables 和 cache 等字段可以影响多个任务。每个 Job 又拥有自己的 stage、script 和 artifacts 等配置。script 中的命令才是 Runner 实际执行的动作。

配置文件放在哪里

　　在 GitLab 项目首页，你看到的通常是仓库文件列表。找到与 src/、tests/ 同级的 .gitlab-ci.yml，开头有一个点，结尾是 .yml。点击文件名可以查看内容，但不要在主分支直接修改。

项目根目录
├── .gitlab-ci.yml
├── requirements.txt
├── src/
└── tests/

　　这不是 Python 脚本。.gitlab-ci.yml 使用 YAML 描述任务，script: 下面的一条条命令才是在终端里执行的 shell 命令。YAML 靠缩进表达归属，本书统一使用两个空格作为一级缩进，不使用 Tab。例如：

stages: [test]

unit_test:
  stage: test
  image: python:3.12
  script:
    - python -m pip install -r requirements.txt pytest
    - python -m pytest
  1. 第 1 行 stages: [test]：定义一个名为 test 的阶段。它位于顶层，前面没有空格。
  2. 第 3 行 unit_test:：定义一个 Job 名称。名称也在顶层，末尾的冒号表示下面还有它的配置。
  3. 第 4 行 stage: test：前面缩进两个空格，表示该配置属于 unit_test。
  4. 第 5 行 image: python:3.12：指定这个 Job 使用的容器镜像，同样属于 unit_test。
  5. 第 6 行 script:：声明接下来要执行的命令列表。
  6. 第 7、8 行：缩进四个空格并用短横线开头，分别安装依赖、运行测试。两条命令按顺序执行，前一条失败时通常不会继续下一条。

　　不要把 script: 与命令写到同一层，也不要用 Tab 补齐缩进。空格数量或层级错误会改变配置含义，或者让 YAML 无法解析。

　　阅读配置时，先看全局字段，再找与当前问题有关的 Job，最后阅读它的命令。不要从第一行开始逐字硬背，也不要看到一个字段就立即修改。

5.2 触发条件与 rules

　　rules 是 Job 的规则列表，按从上到下的顺序匹配，第一条满足的规则生效。没有规则匹配时，这个 Job 不会加入本次流水线。CI_PIPELINE_SOURCE 表示流水线来源，例如合并请求、推送或定时计划。

unit_test:
  script:
    - python -m pytest
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == "main"'
    - when: never
  1. script：指定这个 Job 需要执行的测试命令。
  2. 第一条 if：合并请求事件创建流水线时，把单元测试加入流程。
  3. 第二条 if：主分支的流水线也加入单元测试。
  4. when: never：前面都不满足时，明确不创建这个 Job。

　　workflow: rules 控制整条流水线是否创建，Job 的 rules 控制某个任务是否加入。先看流水线有没有出现，再检查 Job 有没有出现，可以避免把两个问题混在一起。

　　功能分支推送和合并请求可能对应不同流水线类型。配置不当时，同一提交也可能出现重复流水线，因此新增触发规则后要实际检查流水线列表，不能只看 YAML 语法。

5.3 stages 与 needs

　　stages 定义阶段顺序，stage 把 Job 放入某个阶段。needs 则写明当前 Job 依赖哪些前置 Job，使任务可以按明确依赖提前衔接，而不必等待整个阶段。

stages: [test, build]

unit_test:
  stage: test
  script:
    - python -m pytest

package:
  stage: build
  needs: [unit_test]
  script:
    - python -m build
  1. stages：声明测试阶段在构建阶段之前。
  2. unit_test：在测试阶段执行 pytest。
  3. needs: [unit_test]：构建 Job 必须等 unit_test 成功完成。
  4. package：在构建阶段生成软件包。

　　needs 描述依赖，不会让两个 Job 共用同一工作目录。需要传递文件时，仍应配置 Artifact。默认情况下，Job 会下载 needs 所列前置 Job 的产物。

5.4 artifacts 与 cache 配置

　　下面配置把 dist/ 保存为构建产物，并设置七天后过期。expire_in 是保存期限，过期后平台会清理产物，重要交付文件应按团队策略转入制品库。

package:
  script:
    - python -m build
  artifacts:
    paths: [dist/]
    expire_in: 7 days

　　缓存配置应指向工具真正使用的目录，并用依赖清单生成缓存标识。缓存只负责加速，不能作为构建结果的传递通道。第 3 章的完整片段已经展示了 pip 缓存目录与 cache.paths 的对应关系。

5.5 手动任务

　　手动任务适合耗时评估、候选版本构建或发布等需要人工决定时机的操作。任务会等待有权限的人在页面上点击运行。

regression:
  stage: test
  when: manual
  allow_failure: true
  script:
    - python -m pytest tests/regression/
  1. when: manual：不自动执行，等待人工点击。
  2. allow_failure: true：允许这个手动任务不运行或失败而不阻塞整体结果，适合可选检查。
  3. script：人工启动后，Runner 执行回归测试目录中的测试。

　　需要强制门禁的手动任务不能随便设置 allow_failure: true。发布类任务还涉及权限和环境，修改前先确认团队的发布规则。

5.6 安全修改配置

　　修改团队流水线与修改代码一样需要评审。你可以在本地编辑器修改后推送，也可以使用 GitLab 网页自带的流水线编辑器。后者入口是项目左侧“构建 > 流水线编辑器”，英文为 Build > Pipeline editor。

页面标签你用它做什么
Edit编辑仓库根目录的 .gitlab-ci.yml，查看基础语法检查
Validate点击 Validate pipeline，模拟一次事件并检查配置和依赖是否合理
Visualize查看阶段、Job 以及 needs 依赖关系
Full configuration查看 include 引入并展开后的完整配置
  1. 先读完整配置，找到全局默认值、触发规则和目标任务，确认没有 include 引入的其他配置。
  2. 在页面顶部选择自己的功能分支。没有功能分支时，按第 2 章的方法先在本地创建，避免直接改主分支。
  3. 在 Edit 标签做一个小改动，例如只增加一个检查 Job，不同时重写整条流水线。
  4. 到 Validate 标签检查配置。它主要模拟推送事件，MR 或标签的触发条件仍要通过相应真实流水线验证。
  5. 到 Visualize 和 Full configuration 标签检查任务与引入结果。语法通过不代表命令一定成功。
  6. 在页面底部写提交说明并提交到新分支，勾选“使用这些更改发起新的合并请求”。进入 MR 后检查实际流水线，再按团队流程评审合并。

　　include 表示引入其他本地或远程 CI 配置。团队项目常把公共规则放在共享模板中，因此根目录文件不一定包含全部内容。

5.7 常见配置错误

现象优先检查处理方式
整条流水线没有出现workflow: rules、触发来源、配置是否在当前提交中核对事件与条件，不要盲目新增任务
流水线存在但缺少 JobJob 的 rules 是否匹配对照流水线来源逐条判断
同一改动出现重复流水线分支与合并请求规则是否同时命中按团队策略排除重复触发

本章小结

　　阅读 GitLab CI 配置时，先看流水线规则，再看 Job 规则、依赖和命令。修改后用配置检查工具与真实流水线共同验证，不能只凭 YAML 外观判断结果。

  • workflow: rules 控制流水线，Job 的 rules 控制任务。
  • stages 组织阶段，needs 指定精确依赖。
  • Artifact 保存结果，Cache 加速，手动任务等待人工启动。
  • 配置也要经过小改动、验证和代码评审。

第 6 章　流水线的日常操作

面向算法与软件开发者　·　预计阅读 16 分钟　·　目标是能查看、修复、重跑和取证

　　日常使用 CI 的主要动作不是改配置，而是查看状态、打开失败日志、修复代码、重新验证，以及下载产物或启动手动任务。

  1. 6.1 看懂流水线与 Job 状态：先判断当前处于哪一步。
  2. 6.2 阅读失败日志：从第一条有效错误开始。
  3. 6.3 修复后重新验证：本地检查，再推送新提交。
  4. 6.4 什么时候可以重跑：区分环境故障和代码失败。
  5. 6.5 产物、手动任务与取消：完成常见页面操作。
  6. 6.6 怎样向同事反馈问题：提供可定位的信息。

6.1 看懂流水线与 Job 状态

　　在项目左侧选择“构建 > 流水线”，英文界面是 Build > Pipelines。也可以从 MR 的流水线区域进入。列表中的一行代表一次流水线，不是一行代码或一个测试。

  1. 左侧“状态”显示整条流水线是否通过或失败。红叉表示失败，绿色勾表示通过，但阅读时仍要核对对应提交。
  2. “流水线”一列包含编号、提交说明、关联 MR 和缩短的提交 SHA。点击流水线编号进入详情页。
  3. “阶段”一列的每个图标对应一个 Job。鼠标悬停可查看任务名称，点击某个失败图标可直接进入该 Job 的日志。
  4. 右侧下载图标用于获取产物，只有任务实际生成了可下载产物才有内容。播放、重跑或取消等操作取决于状态和权限。

　　看到多条记录时，先核对分支和提交 SHA，确认你看的是最新一次提交。不要只凭一个总状态判断全部细节。

状态含义你接下来做什么
runningRunner 正在执行等待或打开日志观察进度
pending等待可用 Runner长时间不变时检查 Runner 状态与标签
success该 Job 的命令成功完成继续检查其他任务和评审状态
failed命令失败或执行环境出错打开该 Job，定位有效错误
manual等待人工启动确认是否需要运行以及自己是否有权限
skipped因条件或前置结果被跳过检查规则和依赖，不当作通过
canceled被用户或系统取消确认取消原因，必要时重新运行

6.2 阅读失败日志

　　日志通常先显示 Runner 拉取代码、准备镜像和安装依赖，然后执行 script 中的命令。先找到哪一步失败，再找该步骤的第一条有效错误。最后一行常只是“命令返回失败”，不一定是真正原因。

真实的 GitLab Job 日志长什么样

  1. 中间最大的区域是 Runner 的实际输出。$ 开头的行是正在执行的命令，后面的行是命令结果。左侧数字是日志行号，右侧时间是该条输出的时间。
  2. 日志顶部的搜索框可搜索 FAILED、Error 或错误码。搜索只帮助定位，仍要阅读命中位置前后的上下文。
  3. 图中第 70 行说明具体原因：任务期待 Merged Results 流水线，实际得到的引用不符合预期。第 71 行给出项目自己的处理提示。这两行比最后的退出码更有用。
  4. 最后的 ERROR: Job failed: exit code 1 表示命令以失败状态结束。它是结果摘要，不是这次失败的根本原因。
  5. 右侧可核对 Runner、流水线来源、提交 SHA 和关联 MR。向同事反馈时，应提供 Job 页面链接和提交信息，不要只截最后几行。

　　如果看到的是代码或测试问题，就回到本地修改并推送。如果日志显示权限、Runner 或平台服务问题，保留链接并联系对应维护者。完整搜索和显示原始日志等按钮的位置可能随版本变化，以页面工具栏为准。

日志线索通常表示优先检查
FAILED tests/...某个测试断言失败输入、预期结果与本次代码改动

exit code 1命令以通用失败状态结束继续向上找具体错误，不能只看这一行

6.3 修复后重新验证

　　能在本地复现时，先修复并运行与 CI 相同或更聚焦的命令。下面四行是一个完整修复提交过程：

python -m pytest tests/test_preprocess.py -x
git add src/preprocess.py tests/test_preprocess.py
git commit -m "修复空输入的归一化处理"
git push
  1. python -m pytest tests/test_preprocess.py -x：运行相关测试，-x 表示遇到第一个失败就停止，便于集中处理。
  2. git add ...：把功能修复和对应测试一起放入暂存区，路径按实际改动调整。
  3. git commit ...：创建说明清晰的本地修复提交。
  4. git push：推送到原功能分支，让同一 PR/MR 基于新提交重新检查。

　　推送后回到 PR/MR，确认新流水线对应新的提交 SHA。旧流水线失败记录仍然保留，它能帮助追溯，但不要误把旧结果当作新结果。

6.4 什么时候可以重跑

　　重跑会在原流水线的同一提交上再次执行，适合 Runner 临时故障、外部服务短暂不可用、依赖源网络异常等情况。代码断言稳定失败时，重跑通常只会重复同样结果。

　　重跑前先保存第一条有效错误。如果同一提交多次出现不同结果，要记录为偶发问题，检查网络、共享数据、随机种子和并发资源，不要用反复重跑掩盖不稳定测试。

6.5 产物、手动任务与取消

　　下载产物时，可以从流水线列表右侧的下载图标进入，也可以打开生成该文件的 Job，在详情页选择 Download。想先查看压缩包内有哪些文件，选择 Browse。项目的“构建 > 产物”页面，即 Build > Artifacts，可以集中浏览各 Job 的产物。

　　核对提交和任务名称再下载。测试报告、评估结果和构建包可能分别来自不同 Job。产物有保存期限，过期后需要重新生成。没有配置 artifacts 的 Job 不会自动提供你本地目录中的所有文件。

　　手动任务在流水线图中显示播放按钮，点击 Run 才会启动。启动前看清目标环境、变量和提交，尤其不要把生产发布当作普通测试随意点击。

　　取消流水线会停止尚未完成的任务。自己的功能分支出现更新提交时，取消旧检查可以节省资源。涉及共享构建或发布的流水线，先确认影响再取消。

6.6 怎样向同事反馈问题

　　需要帮助时，提供足够让同事定位的信息，避免只发一句“CI 挂了”。推荐包含：

  • 链接：PR/MR、流水线和失败 Job 的页面链接。
  • 版本：分支名称、提交 SHA，以及是否是最新提交。
  • 错误：第一条有效错误及必要的上下文，脱敏后再分享。
  • 复现：本地是否能复现，使用了什么命令和 Python 版本。
  • 已尝试：做过的修复、重跑结果，以及怀疑的代码或环境范围。

　　这些信息能把讨论从“流水线坏了”缩小到“某个提交、某个任务、某条错误”，减少同事反复追问。

本章小结

　　日常操作可以固定为：核对提交，找到失败 Job，阅读第一条有效错误，本地复现修复，推送后检查新流水线。环境故障可以考虑重跑，代码问题应修复后再验证。

  • pending 多表示等待 Runner，failed 需要阅读具体日志。
  • 最后一行退出码通常不是完整原因，要向上找第一条有效错误。
  • 重跑使用原提交，推送修复会形成新提交和新流水线。
  • 反馈问题时提供链接、版本、错误、复现命令和已尝试操作。

第 7 章　多人协作规则与注意事项

面向算法与软件开发者　·　预计阅读 17 分钟　·　目标是安全地参与团队维护

　　CI 能自动检查代码，但团队仍需要约定谁能合并、怎样处理冲突、如何保护密钥，以及怎样让不同电脑得到一致结果。

  1. 7.1 主分支保护与合并门禁：理解为什么检查未过不能合并。
  2. 7.2 小提交与小合并请求：降低评审和回退成本。
  3. 7.3 同步主分支与处理冲突：把冲突解决在功能分支。
  4. 7.4 密钥与敏感信息：避免把凭证交给仓库和日志。
  5. 7.5 固定依赖与可重复环境：减少环境差异。
  6. 7.6 配置评审与故障沟通：明确责任与协作边界。

7.1 主分支保护与合并门禁

　　主分支保护是平台对重要分支设置的限制，例如禁止直接推送、禁止强制推送，或要求通过合并请求进入。合并门禁是允许合并前必须满足的条件，例如 CI 成功、一定数量的评审批准、讨论已解决。

在 GitLab 哪里看这些规则

　　当前 GitLab 的项目入口通常是“设置 > 仓库”，展开“分支规则”。英文路径是 Settings > Repository > Branch rules。选择 main 的规则，可以看到谁允许合并、谁允许直接推送和合并，以及是否允许强制推送。

  1. 有维护权限的同事进入上述页面，点击 Add branch rule 添加规则，或打开已有的 main 规则。
  2. Allowed to merge 控制谁可以通过 MR 合并，Allowed to push and merge 控制谁可以直接推送并合并。若要求所有改动都走 MR，后者通常设为 No one。
  3. 在“设置 > 合并请求”检查合并条件，例如流水线必须成功、所有讨论必须解决。审批数量等能力还与 GitLab 版本和套餐有关。
  4. 普通开发者主要查看结果并遵守规则。看不到“设置”或无法编辑，通常说明没有 Maintainer 或 Owner 等所需角色，请联系负责人，不要自行绕过。

　　这些规则通常由项目负责人或管理员配置。旧版本可能仍显示“受保护分支”或 Protected branches 页面，位置略有差异。门禁未通过时，应修复检查或完成评审，不要寻找绕过方法。

　　CI 成功只是合并条件之一。测试没有覆盖的算法逻辑、接口兼容性和数据风险，仍需要评审人员判断。

7.2 小提交与小合并请求

　　提交是本地版本记录，合并请求是团队评审一组提交的方式。一个提交尽量围绕一个明确动作，一个合并请求尽量围绕一个可说明的目标。提交可以多个，合并请求不必每提交一次就新建一个。

  • 适合放在一个合并请求：修复归一化空输入、补充对应测试、更新相关说明。
  • 适合拆开：归一化修复与无关的界面重构，或功能修改与大规模依赖升级。
  • 提交前检查：临时调试文件、个人数据、模型权重和密钥不应误加入。

　　小改动更容易评审、测试和回退。需要拆分工作时，按可验证的功能边界拆，不要为了凑数量制造许多无意义提交。

7.3 同步主分支与处理冲突

　　任务持续时间较长时，主分支可能已经有别人的改动。可以在功能分支合并最新主分支，提前处理冲突。冲突表示 Git 无法自动判断同一处内容应保留哪种修改，需要人来决定。

git switch main
git pull origin main
git switch feature/normalize-input
git merge main
python -m pytest
git add src/preprocess.py
git commit -m "合并主分支并解决预处理冲突"
git push
  1. git switch main：先切回本地主分支。
  2. git pull origin main：获取远程主分支的最新改动。
  3. git switch feature/normalize-input：回到自己的功能分支。
  4. git merge main：把最新主分支合并进功能分支。若出现冲突，先解决再继续。
  5. python -m pytest：验证合并后的代码仍能正常工作。
  6. git add src/preprocess.py：冲突解决后，把对应文件标记为已处理，路径按实际情况填写。
  7. git commit ...：冲突导致合并暂停时，用提交完成合并。没有冲突且已自动提交时，可跳过第 6、7 行。
  8. git push：把同步后的功能分支推送，重新运行 CI。

　　解决冲突时，先用 git status 找出冲突文件，再检查 <<<<<<<、=======、>>>>>>> 标记两侧的内容。保留正确逻辑并删除标记，不能简单全选自己或全选对方。尚未完成时可以按团队指导使用 git merge --abort 放弃本次合并。

7.4 密钥与敏感信息

　　密码、访问令牌、私钥和内部数据地址应通过平台的变量或密钥管理功能提供。GitLab 项目的入口通常是“设置 > CI/CD”，展开“变量”，即 Settings > CI/CD > Variables。只有具备相应项目角色的成员才能查看或维护这些设置。

　　添加变量时填写键名和值，按团队要求启用遮罩或保护。遮罩用于减少日志中的明文展示，保护用于限制变量可被哪些受保护分支或标签使用。普通测试通常不需要接触生产凭证，不要为了跑通测试而随意申请高权限密钥。

　　不要在测试中打印完整凭证，也不要把包含生产数据的文件提交到仓库。分享日志时先脱敏，尤其是请求地址、请求头和用户信息。

　　如果密钥已经泄露，应立即通知负责人并按流程吊销或轮换。仅删除文件或再提交一次“删除密钥”不会抹去 Git 历史中的旧内容。

7.5 固定依赖与可重复环境

　　可重复环境指同一提交在不同时间和机器上能按相同依赖与数据运行。依赖漂移会使昨天通过的代码今天失败，因此团队会固定 Python 版本、关键依赖、容器镜像和测试数据版本。

  • package==1.2.3 表示固定直接依赖版本，requirements.txt 常用来记录这些要求。
  • 锁文件进一步固定直接和间接依赖，让完整安装结果更稳定，具体格式由项目工具决定。
  • 容器镜像避免随意使用会变化的 latest，测试数据避免依赖个人电脑上的绝对路径。
  • 升级依赖应在独立合并请求中完成，并运行完整相关测试。

7.6 配置评审与故障沟通

　　CI 配置、依赖清单和测试脚本也属于代码。修改后应经过同样的评审和验证，不能因为“只是改流水线”就直接提交到主分支。

　　代码问题通常由提交者修复，共享 Runner、权限和平台故障由对应维护者处理。判断不清时，把失败链接、提交 SHA、第一条有效错误和本地复现情况发出来，团队更容易分工。

　　不要为了赶进度随意删除测试、降低阈值或关闭门禁。确需调整时，应在合并请求中写明理由、影响范围和后续补救，由团队共同确认。

本章小结

　　多人协作的关键是清楚边界：功能分支承载改动，CI 与评审共同验证，满足门禁后合并。遇到冲突、密钥泄露和环境差异时，按团队规则处理，不用绕过检查换取短暂通过。

  • 主分支保护和合并门禁由团队维护，普通开发者不自行绕过。
  • 小提交、小合并请求和对应测试能降低协作成本。
  • 冲突需要人判断，密钥泄露需要吊销或轮换。
  • 固定依赖、配置评审和完整故障信息有助于长期维护。

第 8 章　常见问题与排查方法

面向算法与软件开发者　·　预计阅读 18 分钟　·　目标是建立稳定的排查顺序

　　CI 报错看似很多，排查时可以先分成几类：流水线没有触发、任务等待 Runner、命令执行失败，或者本地与 CI 的环境不一致。

  1. 8.1 先按层级缩小范围：事件、配置、Runner、命令。
  2. 8.2 本地通过但 CI 失败：比较真实环境差异。
  3. 8.3 依赖与模块问题：检查安装和导入两条链路。
  4. 8.4 路径、数据与缓存：确认输入真实存在且一致。
  5. 8.5 未触发、一直等待或缺少 Job：分别检查规则和资源。
  6. 8.6 偶发失败与耗时过长：记录不稳定性并测量瓶颈。
  7. 8.7 实用诊断命令：用输出支持判断。

8.1 先按层级缩小范围

　　先确认分支和提交，再看流水线是否创建。没有流水线时检查触发规则。流水线存在但一直等待时检查 Runner。Job 已失败时才进入日志分析。这个顺序能避免在代码里寻找实际上由权限或资源造成的问题。

　　每次只验证一个主要假设。记录你看到的证据和做过的修改，否则同时改依赖、代码和配置后，即使通过也很难知道真正原因。

8.2 本地通过但 CI 失败

　　“本地通过”只说明你电脑上的某套环境通过。CI 可能使用不同操作系统、Python 版本、依赖版本、文件路径和权限。先比较环境，再判断代码是否有跨平台问题。

差异常见表现检查方法
Python 或依赖版本语法、API 或数值结果不同对比版本输出和依赖清单
操作系统路径分隔符、文件名大小写行为不同使用项目路径工具，检查真实文件名
工作目录相对路径找不到文件打印当前目录，确认命令从哪里执行
环境变量与权限本地能访问服务，CI 被拒绝检查变量是否存在及当前分支权限
本地未提交文件本地测试完整，CI 缺数据或模块检查 Git 是否实际跟踪这些文件

　　Linux 文件名通常区分大小写，Windows 常见文件系统通常不区分。Data.csv 与 data.csv 在本地可能被当成同一个文件，在 CI 的 Linux Runner 中却不同。

8.3 依赖与模块问题

　　依赖没有安装与模块无法导入是两个相邻但不同的环节。安装失败先看 pip 输出、版本约束和网络来源。安装成功后出现 ModuleNotFoundError，再检查包名、项目安装方式和导入路径。

  • 找不到依赖：检查 requirements.txt 是否包含它，安装步骤是否在同一 Job 中成功。
  • 版本冲突：阅读解析器提示，确认哪些包要求了不兼容版本，不要直接全部升级到最新版。
  • 项目模块找不到：采用 src 目录布局时，通常需要安装项目本身或正确配置导入路径。
  • 私有源不可达：检查 CI 网络、认证变量和访问权限，不要把私有令牌写进仓库。

　　修改依赖时保留失败输出，并单独提交依赖变化。这样既方便评审，也能在升级引入问题时快速定位。

8.4 路径、数据与缓存

　　代码中的相对路径取决于命令执行时的当前目录，不完全取决于文件所在位置。团队常约定从仓库根目录运行命令，并用项目路径构造数据位置。个人电脑上的 D:\data 或 /home/name/data 不应成为 CI 的隐含前提。

　　测试数据没有随仓库提交时，本地存在的文件不会自动出现在 Runner 中。小测试样例可以纳入仓库，大数据集应通过团队规定的存储与下载流程提供，并记录版本。

　　缓存损坏或复用了不合适的内容时，可能导致安装异常。先核对缓存标识、依赖文件和实际目录，再考虑清除对应缓存。缓存只是加速手段，不能在每次失败时都先清缓存，也不能用缓存传递测试报告。

8.5 未触发、一直等待或缺少 Job

　　流水线没有创建时，检查当前提交是否包含有效 CI 配置、项目的 CI 功能是否启用，以及 workflow: rules 是否允许当前事件。流水线存在但缺少 Job 时，再检查该 Job 的 rules。

　　任务一直处于 pending 时，检查可用 Runner 是否在线、是否接受该项目，以及标签是否匹配。Runner 标签用于选择具备特定系统、硬件或权限的执行资源。任务要求 GPU 标签，而在线 Runner 没有这个标签时，任务可能持续等待。

　　没有权限查看或修改 Runner 时，把 pending 任务链接、等待时长和所需标签提供给维护者。不要随意删除标签让任务跑在不符合要求的机器上。

8.6 偶发失败与耗时过长

　　偶发失败常叫 flaky test，指同一提交在输入看似不变时，多次运行出现不同结果。常见原因包括随机数、测试执行顺序、共享文件、外部服务、系统时间和并发资源。

　　处理偶发失败时，保存成功与失败日志，记录随机种子、输入数据和运行时间，尽量稳定复现。自动重试可以应对明确的外部临时故障，但不能替代修复不稳定的测试。

　　耗时过长时，先用测试耗时报告和 Job 日志找出慢在哪里，再考虑缩小测试数据、拆分独立任务、并行执行或增加合理缓存。优化前先测量，不要凭感觉删除慢测试。

8.7 实用诊断命令

　　下面命令用于收集证据，不会自动修复问题。在本地或允许调试的 Runner 环境中按需执行：

python --version
python -m pip check
python -m pytest --collect-only -q
python -m pytest tests/ --durations=10
  1. python --version：确认实际使用的 Python 版本，与 CI 镜像和项目要求对比。
  2. python -m pip check：检查当前环境中已安装包的依赖要求是否存在冲突或缺失。
  3. python -m pytest --collect-only -q：只收集并列出测试，不执行测试，可排查“没有发现测试”或发现范围错误。
  4. python -m pytest tests/ --durations=10：执行测试并列出最慢的十项，用于定位耗时热点。

　　诊断命令的输出应与失败 Job、提交 SHA 一起记录。只保留“最后又成功了”无法帮助团队预防下一次问题。

本章小结

　　排查 CI 问题时，先判断流水线是否创建、Runner 是否可用，再进入日志定位代码、依赖、数据或权限问题。每次根据证据验证一个假设，避免盲目重试和同时修改多处。

  • 本地与 CI 不一致时，先比较版本、系统、路径、变量和未提交文件。
  • 未触发看流水线规则，缺 Job 看任务规则，pending 看 Runner 和标签。
  • 缓存只用于加速，偶发失败要记录并复现，慢测试先测量再优化。
  • 保留诊断输出，让修复经验能够被团队复用。

第 9 章　完整实战：从写代码到合并交付

面向算法与软件开发者　·　预计阅读 35 分钟　·　同一个项目贯穿全部操作

　　本章假设你是团队里的算法开发者。你接到一个任务：为数值归一化函数补充异常输入处理，并用 CI 证明修改没有破坏原有行为。从创建分支到合并后的产物下载，都围绕这一次任务展开。

　　你不需要已有 CI 使用经验。每节先说明当前要做什么，再给出文件或命令，最后解释产生了什么结果。示例使用 Windows 的 Git Bash 和 GitLab，团队实际界面与规则可能略有不同。

  1. 9.1 案例目标、角色与项目目录：知道这次任务由谁完成。
  2. 9.2 创建功能分支：从最新主分支开始工作。
  3. 9.3 编写功能代码：先让输入规则和输出行为明确。
  4. 9.4 编写并理解测试：把预期行为写成可重复检查。
  5. 9.5 配置依赖与打包：让本地和 CI 使用同一套项目描述。
  6. 9.6 在本地完整验证：亲手跑通 CI 将重复执行的命令。

9.1 案例目标、角色与项目目录

9.3 编写功能代码

　　先把任务要求转成明确规则：正常输入得到比例，空输入返回空列表，无法合理计算的输入给出异常。下面是 src/algorithm_demo/preprocess.py 的完整内容：

import math


def normalize(values: list[float]) -> list[float]:
    if not values:
        return []
    if any(not math.isfinite(value) for value in values):
        raise ValueError("输入必须都是有限数值")
    total = sum(values)
    if total == 0:
        raise ValueError("总和为 0 时无法归一化")
    return [value / total for value in values]
  1. import math：引入数学工具，后面用 math.isfinite 排除 NaN 和无穷。
  2. 函数声明：list[float] 表示输入和输出都是浮点数列表，函数名 normalize 表示归一化。
  3. 前两个判断：空列表直接返回，包含非有限数值时抛出 ValueError，避免继续产生无效结果。
  4. 最后两步：先求总和并拒绝除以零，再逐项除以总和，形成归一化结果。

　　例如输入 [1.0, 3.0]，总和是 4，输出就是 [0.25, 0.75]。这个明确例子稍后会同时出现在测试和本地验证中。

9.4 编写并理解测试

　　测试把刚才的规则写成机器可以重复执行的断言。断言就是“实际结果必须符合这个预期，否则测试失败”。测试文件由你编写，CI 以后只负责调用它。

　　下面是 tests/test_preprocess.py 的完整内容：

import math

import pytest

from algorithm_demo.preprocess import normalize


def test_normalize_values():
    result = normalize([1.0, 3.0])
    assert result == [0.25, 0.75]
    assert math.isclose(sum(result), 1.0)


def test_empty_input():
    assert normalize([]) == []


def test_rejects_nan():
    with pytest.raises(ValueError, match="有限数值"):
        normalize([1.0, float("nan")])


def test_rejects_zero_sum():
    with pytest.raises(ValueError, match="总和为 0"):
        normalize([-1.0, 1.0])

　　pytest 按命名规则发现 test_*.py 文件和以 test_ 开头的函数。assert 检查正常结果，pytest.raises 检查预期异常是否发生。四个测试各自回答一个问题：

测试函数输入预期结果防止什么问题
test_normalize_values[1.0, 3.0][0.25, 0.75]，总和接近 1正常计算逻辑被改错
test_empty_input[][]空输入触发异常
test_rejects_nan包含 NaN抛出“有限数值”异常无效数值进入后续流程
test_rejects_zero_sum[-1.0, 1.0]抛出“总和为 0”异常发生除以零

　　如果后续有人修改归一化逻辑，这些测试会重新检查同样的输入和预期。CI 的价值就是让这套检查在团队环境中重复发生，而不是只存在于你的电脑上。

9.6 在本地完整验证

　　本地验证的目的，是在把代码交给团队之前，先亲手跑通 CI 稍后会重复执行的命令。建议在虚拟环境中操作，避免项目依赖污染系统 Python。

第一步：创建并激活虚拟环境

  3. python --version：确认后续命令使用预期的 Python 版本。

　　.venv 是本地环境目录，不属于项目源代码，不应提交到仓库。团队已有虚拟环境和忽略规则时，直接使用团队方式。

9.7 理解 CI 配置与执行过程

　　下面的 .gitlab-ci.yml 把本地验证拆成三个 Job。触发范围是合并请求、默认分支和版本标签。功能分支尚未创建合并请求时，本例不会因普通推送创建流水线。

workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
    - if: '$CI_COMMIT_TAG'

stages: [check, test, build]

default:
  image: python:3.12
  before_script:
    - python -m pip install -r requirements.txt
    - python -m pip install -e .

variables:
  PIP_CACHE_DIR: "$CI_PROJECT_DIR/.cache/pip"

cache:
  key:
    files: [requirements.txt]
  paths: [.cache/pip]

lint:
  stage: check
  script:
    - python -m ruff check .

unit_test:
  stage: test
  script:
    - python -m pytest --junitxml=report.xml
  artifacts:
    when: always
    paths: [report.xml]
    reports:
      junit: report.xml

package:
  stage: build
  needs: [unit_test]
  script:
    - python -m build
  artifacts:
    paths: [dist/]
    expire_in: 7 days

　　CI_DEFAULT_BRANCH 是平台提供的默认分支名称，因此配置不用写死 main。before_script 为每个 Job 安装相同环境，三个 Job 分别负责静态检查、单元测试和构建。

　　测试报告成功或失败都会保存，构建 Job 等单元测试成功后执行。产物只保存七天，实际项目应按团队交付策略调整。合并前仍要通过 CI Lint 和真实流水线验证。

三个 Job 实际怎样运行

　　你在后面创建 MR 时，GitLab 发现流水线来源是 merge_request_event，第一条规则匹配，于是基于这次提交创建流水线。平台再按照阶段和依赖安排 Job，Runner 执行其中的命令。

执行顺序Runner 做什么成功后留下什么失败时看什么
1. lint拉取提交，准备 Python 3.12，安装依赖和项目，执行 Ruff静态检查通过状态具体文件、行号和检查规则
2. unit_test在新的任务环境中重新安装，执行 pytest四个测试结果和 report.xml失败测试、输入、预期和实际异常
3. package等单元测试成功，执行构建dist/ 中的 wheel 和 sdist打包配置、缺失文件或构建错误

　　每个 Job 都有自己独立的准备过程。CI 不会使用你电脑里的 .venv，也不会自动拿到你本地生成的 report.xml 和 dist/。Runner 读取的是本次提交中的源代码、测试和配置，再重新生成这些结果。

　　pip 缓存只用于减少依赖下载时间。测试报告通过 Artifact 保存，软件包也通过 Artifact 保存。三者用途不同，不能混为一谈。

9.9 经历一次失败与修复

　　下面用另一种情况演示失败路径：第一版函数漏掉了空列表处理，而你只运行了正常输入测试就提交，所以本地没有发现问题。创建 MR 后，lint 通过，但 unit_test 失败，依赖它的 package 不会执行。前文是顺利通过的完整路径，本节专门练习失败后的修复闭环。

第一步：从 MR 找到失败 Job

　　先核对流水线对应最新提交，再打开 unit_test。不要先打开已经通过的 lint，也不要只看流水线首页的“失败”两个字。

Job此时状态原因
lintsuccess静态检查没有发现基础代码问题
unit_testfailed空输入测试没有得到预期结果
packageskippedneeds 指定的单元测试没有成功

第二步：读懂关键日志

　　日志格式会随工具版本变化，本例需要关注的关键内容如下：

tests/test_preprocess.py::test_empty_input FAILED
E   ValueError: 总和为 0 时无法归一化
=========================== short test summary info ===========================
FAILED tests/test_preprocess.py::test_empty_input
  1. 第一行指出失败的测试是 test_empty_input，所以排查范围是空列表行为。
  2. ValueError 是实际异常。测试原本期待返回 []，函数却继续求和并拒绝了零总和。
  3. 最后的汇总再次指出失败测试，真正需要修复的是空输入分支，不是 Runner，也不是 pytest。

第三步：在本地复现同一个失败

python -m pytest tests/test_preprocess.py::test_empty_input -x

　　文件路径后的 ::test_empty_input 表示只运行这个测试，-x 表示遇到第一个失败就停止。能复现同样异常，说明你和 CI 在讨论同一个问题。

第四步：修改代码并完整验证

　　在计算总和之前补回下面的分支。测试已经准确描述了预期行为，因此这次只需要修改功能代码：

if not values:
    return []

　　然后按顺序执行下面五行：

python -m pytest tests/test_preprocess.py::test_empty_input
python -m pytest
git add src/algorithm_demo/preprocess.py
git commit -m "修复空列表的归一化处理"
git push
  1. python -m pytest ...::test_empty_input：先确认刚才失败的单个测试已经通过。
  2. python -m pytest：再运行全部测试，确认修复没有影响其他输入。
  3. git add ...：只暂存这次功能修复。
  4. git commit ...：创建一个新的修复提交，原提交仍保留在历史中。
  5. git push：推送到原功能分支。前面已建立跟踪关系，所以不需要再次写 -u。

第五步：确认原 MR 中的新结果

　　MR 跟踪的是功能分支。分支出现新提交后，原 MR 会更新并触发新流水线，不需要删除或重新创建 MR。旧失败记录仍然保留，你需要核对新提交 SHA 和新流水线状态。

　　这次 lint 和 unit_test 通过后，package 才会运行。三个 Job 全部成功，只表示配置的自动检查已经通过，接下来还要完成团队评审。

9.10 评审、合并与获取结果

评审人员继续检查什么

　　评审同事会看到同一份代码和 CI 结果，继续判断空列表返回空列表是否符合任务约定、异常提示是否清楚、测试是否覆盖关键输入。CI 无法替人判断这些设计与业务问题。

　　如果同事问“为什么空列表返回空列表，而不是抛出异常”，你可以在 MR 中回复任务约定，并指向 test_empty_input。讨论和修改都留在同一个 MR 中，下一位同事才能理解决策依据。

谁执行合并

　　当 CI 成功、评审批准且其他门禁满足后，由团队授权的人点击合并。某些项目允许提交者自己合并，另一些项目要求负责人合并，以团队权限为准。CI 默认不会因为你看到三个成功 Job 就自动合并。

结果文件从哪里下载

需要的内容来自哪个 Job文件用途

　　在 MR 的流水线区域进入最新流水线，点击 package 这个 Job。详情页的 Download 用于下载产物压缩包，Browse 用于先浏览包内文件。压缩包里的 dist/ 才对应上表中的 wheel 和源代码发行包。需要测试报告时，打开 unit_test 的产物，而不是 package。

　　也可以从项目左侧“构建 > 产物”进入，按 Job 找到文件。下载前核对提交和 Job，避免拿到旧流水线的结果。这里的文件由 Runner 重新生成，不是你本地目录被直接上传。

  1. git switch main：从功能分支切回本地主分支。
  2. git pull origin main：把团队远程主分支的最新状态同步到本地，包括刚合并的改动。
  3. git branch -d feature/safe-normalize：删除已经不再需要的本地功能分支，不会删除远程分支。

开始一项改动

  • 同步默认分支，确认工作区状态，创建含义明确的功能分支。
  • 同时修改功能与对应测试，避免提交个人文件、数据和密钥。
  • 在本地运行相关检查，提交前查看变更范围。

修改 CI 配置

  • 阅读完整配置与引入模板，确认触发、依赖、路径和权限。
  • 小范围修改，先做配置检查，再通过真实流水线验证。
  • 像功能代码一样提交评审，不直接覆盖团队配置。

处理失败

  • 核对提交，打开失败 Job，找到第一条有效错误。
  • 区分代码、依赖、数据、配置和 Runner 问题，每次验证一个主要假设。
  • 本地复现修复后追加提交，推送并检查新流水线。

合并与沟通

  • 在 PR/MR 中写清目的、改动、验证方式和注意事项。
  • 反馈问题时提供链接、提交 SHA、错误、复现命令和已尝试操作。
  • 满足 CI 与评审要求后合并，再同步本地主分支。

本章小结

　　这个案例包含了团队协作的最小完整链路：功能与测试一起准备，本地先验证，CI 在 Runner 中重复执行，失败由提交者修复，评审与检查通过后合并，产物按配置交付。

　　掌握这条链路后，面对真实项目时可以先找到对应文件和命令，再沿用团队现有规则操作。不要追求一次理解所有平台功能，能稳定完成提交、验证、修复和沟通，就已经可以参与日常协作。
